# One product, one release entry point

TIN-407 consolidated npm packaging and review builds. TIN-411 replaced the
all-platform Python wheel bundle with a small product and matching backend
downloads. TIN-413 separates routine source checks from installation
qualification. This guide describes those boundaries; it is not evidence
that a particular candidate has passed CI or been published.

## What users install

```text
npx --yes physicalsystems@preview
```

The npm package contains the Harness, its reviewed JavaScript dependency
closure and exact backend download manifests. On first managed setup, the
Harness selects the matching OS/architecture/Python combination, asks for
software-installation consent, downloads only those pinned files, checks their
sizes and hashes, installs an isolated environment and starts discovery-only
Node supervision. Successful installations are verified and reused on later
launches without repeating the downloads.

Users do not clone a repository, run pip themselves or start a second terminal.
Supported CPython with `venv`/`ensurepip` is still required; this is not a
bundled interpreter or arbitrary hardware-driver installer. Windows ARM64
Harness support does not imply an ARM64 backend wheel set. Runtime is a library
inside the Python Node, not a third server the user must start.

## What maintainers run

Start at the product repository, not at three independent package publishers:

```text
npm run release -- plan
npm run release -- check
npm run release -- prepare --output ABSOLUTE_NEW_ARTIFACT_DIRECTORY
```

`release/product.json` records independent product, Node, Python Runtime and
Pi runtime versions, exact backend pins and the approved selector/toolchain
policy. The plan validates package/lock versions, hash-pinned manifests and
cross-platform wheel identities. It reports unchanged backends as
`reuse-pinned-artifacts`: this does not build Node, invoke private exporters or
start a PyPI release. A changed pin without matching reviewed metadata fails
before dependency preparation. The descriptor is not permission to publish.

`check` also compares the protected workflow's release/toolchain constants to
the descriptor. Those constants remain explicit in the existing publisher;
they are checked for drift, not silently rewritten. This revision is not a
new publisher or a fully automated changed-backend coordinator.

Planning/checking are local and read-only. They do not prove that URLs are
currently downloadable, that a version is unpublished, or that installation
tests have passed. The protected workflow retains its live registry and
exact-artifact checks. Updating the descriptor alone cannot authorize new
backend bytes or move an npm tag.

Use the pinned npm CLI declared by the descriptor for preparation. The
existing CI-compatible alias remains available:

```text
npm run release:prepare -- --output ABSOLUTE_NEW_ARTIFACT_DIRECTORY
```

Preparation bootstraps the reviewed JavaScript dependency tree if needed,
validates pinned backend metadata and packs once. It does not download Python
wheels by default. Output contains the product tarball, checksum manifest and
frozen Pi runtime audit tarball. The latter is checked, not republished.
Generated bytes stay outside the source repository.

The output root also contains `preparation-receipt.json`, binding the local
plan to the generated candidate manifest and its hash. It explicitly records
that installation is not qualified and publication is not authorized. It is
an audit receipt, not a resumable upload token: old CI results are never reused
as evidence for different bytes. Offline review artifacts use their existing
separate evidence and do not receive a normal-product preparation receipt.

For publication, use the existing **Publish Physical Systems npm preview**
workflow on `main`. There is one npm publishing entry point, not separate
manual releases of the Harness, Node and Runtime for an unchanged backend:

```text
Develop: source checks -> review and merge
Release: build once -> qualify exact package -> approval -> publish -> verify
```

The final workflow tests one package across Windows x64/ARM64, Ubuntu
22.04/24.04 and pinned npm 11/12 combinations, plus the unsupported Node.js
regression. After all checks pass, the existing protected environment asks
for human approval. OIDC publishes that exact package to `preview`; registry
integrity, tags and provenance are then verified. No local publishing shortcut,
reusable npm write token, automatic `latest` promotion or component republish
is introduced. See [the release checklist](RELEASE.md) for the exact procedure.

## What got leaner

Ordinary PR and main-branch CI builds one source-review candidate and shares
its checksum-verified dependency closure across the existing four native
platform jobs. It retains source tests, boundary and license checks, SDK
compatibility, native credential tests and the unsupported Node.js regression.
It does not repeat the full local/global/npx installation matrix, backend
downloads or managed first-run acceptance.

That installation qualification belongs to the protected release. A green
source-review run means **source checks passed**, not **installation qualified**
or **published**. It can miss integration failures that are found by the final
release tests; those failures must be fixed before publishing.

The release still builds from the exact approved `main` commit. A PR's test
merge commit and dependency artifact are not promoted into publishing, nor is
a successful PR check substituted for release evidence. This retains a small
review build and one full release-qualification pass rather than repeating
full installation tests in both stages. Actual timing depends on runner and
network performance; no fixed release duration is promised.

## Repositories and components

One product does not make all source public or require identical component
versions:

| Repository | Responsibility in this revision |
| --- | --- |
| `physicalsystems` | Public Harness, product manifests and npm release entry point |
| `runtime` | Public Python execution contracts and reusable kernel |
| `node` | Private hardware host, concrete adapters and reviewed backend builds |
| `node-releases` | Reviewed Node distribution assets and existing Python publisher |

An unchanged backend is reused by exact version, URL and checksum. A changed
Node or Runtime still needs its backend build, export/license review and
verified distribution information before a product release can select it.
Those cross-repository preparation steps have **not** been replaced by a
fully automated coordinator in this revision. There is no monorepo migration,
repository deletion/archive or license change here.

The local planner consolidates the unchanged-backend preparation path only.
The pending source-layout decision is whether to keep Runtime separate or
import its already-public, committed source into the product repository.
Private Node source stays private in either case. Moving the `node-releases`
publisher requires a separate verified identity cutover; old immutable
downloads must remain available throughout that migration.

The next source-consolidation decision must preserve the public/private
boundary. Copying the private Node into this public repository is not a
packaging refactor. Retiring `node-releases` also needs a tested replacement
for its publishing identity and continued availability of old immutable
download URLs; it must not break installed clients.

## Explicit offline preparation

For a separate reviewed offline candidate:

```text
npm run release:prepare -- --output ABSOLUTE_NEW_ARTIFACT_DIRECTORY --offline --wheelhouse ABSOLUTE_REVIEWED_WHEEL_DIRECTORY
```

Omitting `--wheelhouse` allows this explicit offline-artifact builder to fetch
the complete approved wheel closure. `--metadata` and `--wheelhouse` require
`--offline`; neither changes default downloads. Offline candidates carry
backend notices and an SBOM and are not eligible for the small npm publisher.
The normal product has a 50 MiB archive guard; this is project policy, not an
assertion about npm's universal limit.

All modes preserve the component licenses and exact artifact identities.
Installation consent is not permission to open a camera or move a robot.
Software checks do not qualify a physical workcell or prove task success.
